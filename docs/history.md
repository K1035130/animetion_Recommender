无论哪条路径都印证了第 4 节「不建 HNSW」的判断。

**已定的几件事：**

- **打分接口无状态**（第 2 节铁律）：`score(catalog, ratings, ...)`，评分随请求传入。
  本地自测用 JSON 文件、游客用 localStorage、注册用户用 `user_rating` 表，推荐链路一行不改。
  ⚠️ 所以**现在不建 user 表** —— 认证在第 6 周，现在建也没有东西会往里写。
- **权重 `log(1+count) × idf`，行 L2 归一化**。实测 binary 模式结果明显更差
  （日常档案的结果中位热度从 done=9,292 掉到 293），`binary` 保留给第 5 周做 ablation。
- **μ 向先验收缩**：`μ = (Σc·r + k·prior)/(Σc + k)`，`prior=7.07`（全站逐票均分）、`k=2`。
  ⚠️ 不收缩的话**只评一部或所有评分相同时偏好向量整个归零**，问卷答完第一题拿到空结果。
- **三种作答带不同置信度**（见 `questionnaire.to_rating()`）。
  ⚠️ 不区分的话「想尝试(8)」的权重会**高于**「看过并打 7.5」，显然反了。
  ⚠️ 「想尝试」的作品**要留在推荐结果里** —— 那正是用户要的；只有「看过」和「不感兴趣」才剔除。
- **排序 = 两段式召回 + blend**：先按匹配度取 `top_k × 10` 候选，再按
  `α·匹配 + (1-α)·贝叶斯加权评分` 重排（两者先在池内 min-max 归一化，量纲差太远）。
  α 默认 0.5：实测匹配度只掉 1.4%、结果均分涨 0.56。
  ⚠️ `rank_by="match"` 必须保留 —— 第 5 周评测要跑纯 tag 模型做对照。

⚠️ **零向量作品必须排除在候选之外。** 它们与任何偏好向量的余弦都是 0，
而偏好向量整体为负时（用户对问卷多数作品选「不感兴趣」），0 反而**高于**所有
负相关作品，Top5 会变成虫虫危机、隐形墨水这类没有 tag 的条目。

### ✅ 推荐结果加评分下限 `MIN_SCORE = 3.5`（2026-08-12）

**依据是评分信号的不对称性**：高分不保证好看（小众神作与过誉作品混在一起），
但低分几乎必然难看。所以低分可以当硬过滤，高分不能当硬排序。

⚠️ **和「热度权重必须等 baseline」不冲突，但要注意口径。** 那条讲的是把热度
**混进排序**会污染 NDCG 归因；这里是**候选池定义**，对四条 baseline 一视同仁。
`score(min_score=...)` 做成了参数，第 5 周**四条线必须传同一个值**（要么全默认、
要么全传 None），否则候选池不一致，NDCG 没有可比性。

⚠️ **判据是「有评分且低于 3.5」，未评分作品放行。** 写成 `>= 3.5` 会把
未评分作品一并排除，而 `mode="upcoming"` 推的正是还没播的新番。当前 dump 里
那 2 部碰巧有开播前评分（小圆剧场版 8.1、上低音号后篇 5.2），所以现在看不出问题，
但第 6 周季度同步接进真正的新公布作品后，upcoming 档会被**静默清空**。

⚠️ **必须用原始均分，不能用 `wr`。** wr 向 7.07 收缩，60 票打 3.0 的作品
wr 高达 6.39，按 wr 卡这条线等于什么都没过滤。

实测：库内低于 3.5 的共 **78 部（0.68%）**，最热门的是三体(1.70)、
兽娘动物园2(1.40)、约定的梦幻岛第二季(3.30)、国王游戏(2.70)，全是公认翻车作。
其中 26 部票数不足 100（最少 25 票），单看统计噪声偏大，
但误伤几部冷门作品的代价远小于推出一部烂片。

**为什么 tag 余弦特别容易踩这个坑**：烂续作的题材标签与前作几乎相同，
向量上和用户口味高度吻合 —— 烂的是执行不是题材。实测「只给约定的梦幻岛打 9 分」，
关掉下限时第二季以 **match=0.983 排在第 1 位**。

⚠️ **续作折叠挡不住这种情况，而且会加剧它。** 折叠逻辑是「换成系列里用户
**还没作答过**的最早一部」，而用户恰恰给第一季打了分 → 第一季作为「已看过」被剔除
→ 第二季反而成了该系列的入口。「给第一季打高分」正是最常见的情形。

实测各场景（默认配置）低分作品漏出数：

| rank_by | 开下限 | 关下限 |
|---|---|---|
| `blend`（用户实际看到的） | 0 | **0** —— 质量项已把低分压下去 |
| `match`（第 5 周 baseline 用） | 0 | **2**，含第 1 位 |

即 blend 模式下目前是空操作，但 blend 是 α=0.5 的**软加权**不是保证；
`match` 模式下它是唯一防线。

### Tag 词表第二轮清洗（2026-08-11，418 → 308）

第 13 节动作 5 预告的「正路」已经走通：**不再手工枚举人名公司名，改用 dump 的
person 数据自动检测**。方法分两层，缺一不可：

1. **共现检测**：打了 tag T 的作品，是否高度共享同一个 person？
   （`subject-persons` ∪ `person-characters`，后者必需 —— 声优走「作品→角色→声优」
   两跳，只查前者会把中井和哉、坂本真綾 全部漏掉）
2. **名字相似**：共享者的名字是否就是 T 的书写变体？

⚠️ **只做第 1 层会误杀真题材词。** 高产的窄领域创作者会制造假阳性：
`催眠` `肉感丰满` `辣妹` `足交` 全部指向同一个里番监督，`傲娇` 指向钉宫理惠，
`排球` 指向排球少年的原作者。这些都是真题材，必须保留。第 2 层用来区分。

⚠️ **第 2 层挡不住繁简变体**：`冨樫義博` vs `富坚义博` 字符重合率不到 20%。
这批（约 10 个）靠人工核对补上。彻底自动化要引 opencc，为这个规模不值得。

剔除的 110 个里：人名 ~55、IP ~30、公司 6、繁体形态词 4、观看状态/怀旧标记 9、地区 8。

第 9 节已经警告过「问卷抽到系列续作等于白问一题」，但现有对策（限制在 `meta_tags ∩ {TV, WEB}`）**挡不住 TV 续作**。

### ✅ P0 的 tag 向量用 `meta_tags` 兜底（已实现，但效果有限 —— 142 部仍是零向量）

**166 部（1.4%）清洗后 `tags` 为空**（第一轮词表下是 139 部，二轮剔掉 110 个词后增加），
其中包括化物语（done=37,573）。
原因是 dump 的 `tags` 是**截断的 Top-11**，越有名的作品前 11 位越被制作组/监督/CV 占满：

```
化物语的 11 个 tag：新房昭之 西尾维新 化物语 SHAFT 2009年7月 荡漾 TV 战场原大人 花泽香菜 神谷浩史 2009
→ 题材词一个没有，清洗后 = 0 个
```

⚠️ **兜底效果远不如预期（2026-08-11 实测修正）。** 早先记的「这 139 部 100% 都有
`meta_tags`」字面没错，但**有 meta_tags ≠ 有题材类 meta_tags**。二轮清洗后
tags 为空的 166 部里，**只有 24 部（14%）**能靠 meta_tags 拿到非零向量，
其余 142 部的 meta_tags 全是形态+地区（`['TV','中国']`、`['剧场版','欧美','美国']`），
过 classify() 后被分流干净，仍是零向量。

没救回的以**欧美动画和国产老动画为主**：花木兰、狮子王、蓝精灵、虫虫危机、
大头儿子和小头爸爸、海尔兄弟 —— 官方题材标签对非日本作品明显更稀疏。
这 142 部在 P0 里**永远无法被 tag 余弦召回**，只能等第 3 周的 embedding
（简介文本人人都有）。

另外全库清洗后平均只有 **3.8 个**非零维 / 308 维（稀疏度 1.24%），
tag 向量比预想稀疏得多。

### 与本文档原计划的两处偏离（已论证，勿回退）

**① 动作 4 拆成 4a/4b，staff/studio 不走 AniList。**
实测 bangumi-data 能给出 AniList id 的只有 56.4%，且缺口不随机：国产 7.1%、欧美 0.1%、R18 3.0%、OVA 25%。
而 dump 自带的 `subject-persons` + `person` 覆盖 92.3%（公司）/ 93.3%（staff），国产 83.6%、欧美 58.2%。
「喜欢上海美术电影制片厂」是真实口味维度，只走 AniList 会把它整个抹掉。
AniList 保留它真正独有的：`idMal`（Phase 2 锚点）、~~英文名~~、全球热度。

⚠️ **「英文名是 AniList 独有」这条在 2026-08-16 被实测推翻。**
`name_en` 只覆盖 **5,206 / 11,453（45.5%）**，而**库里已有的数据能再挖出 2,962 部**：

```
已有 name_en（AniList english）              5,206   45.5%
+ name 本身就是拉丁字母（欧美/部分国创原名）      +1,410
+ infobox_alias 里的英文写法                  +1,552
────────────────────────────────────────────────────
  零抓取可达                                 8,168   71.3%
```

📌 **欧美那 809 部只有 1 部有 `name_en`，但它们的 `name` 就是英文原名** ——
`Tom and Jerry` · `Arcane` · `Zootopia` · `Wall·E` · `Coco` · `Rick and Morty Season 1`。
**0.1% 那个数字是假象**：AniList 作为日本动画库收不到西方动画，
但 Bangumi 早就存着原名了。⇒ 这一格根本不该去问 AniList。

⚠️ 而且**有 `anilist_id` 也不一定有英文名**：6,445 部有 id，其中 **1,239 部（19%）**
AniList 自己只有 romaji 没有 english —— `backfill_anilist.py` 当初只取了
`title.english`，**没取 `title.romaji`**。

⇒ 结论修正为：**AniList 真正独有的只剩 `idMal` 和全球热度**。英文名它只是来源之一，
且不是最大的那个。详见第四部分「英文名回填」。

**4. P1：融合 staff/studio 结构化特征** —— ✅ **已完成（2026-08-14）**

```
match = (Σ wᵢ·cosᵢ) / Σ wᵢ            三路各自归一化后加权，再按参与权重归一
rank_score = α·match + (1−α)·quality   现有 blend 结构不变
默认 w_tag=0.3 / w_emb=0.6 / w_staff=0.1（⬜ 占位值，第 5 周要扫）
```

产出：`staff_vec sparsevec(1933)` 10,269 行 + `data/interim/staff_vocab.json`
（[sql/006](../sql/006_staff_vec.sql) · [src/staffvec.py](../src/staffvec.py) ·
[scripts/build_staff_vectors.py](../scripts/build_staff_vectors.py)），
两条打分路径都改（[src/recommend.py](../src/recommend.py) 的 `Weights`/`_cosines` +
[src/recommend_sql.py](../src/recommend_sql.py) 的动态 match 表达式），
API 暴露 `w_tag/w_emb/w_staff`（**第 5 周跑四条 baseline 的入口**）。

**三个设计决定：**

- **三个空间分开算余弦，不拼成一个大向量。** 拼接等于让 308 维 tag 和
  1024 维 embedding 按维数比例隐式分权重，而我们要的是显式可调、可扫描的权重。
- **μ 只算一次、三路共用。** 各空间各算各的 μ 的话，同一条评分在 tag 空间是
  「喜欢」、在 embedding 空间可能变成「不喜欢」，融合出来没有意义。
- ⚠️ **某一路偏好向量为零时整项跳过，不是当成 0 相似度。** 贡献 0 会对所有
  作品一视同仁地稀释另外两路。而且 **pgvector 对零向量的 `<=>` 返回 NaN**，
  `ORDER BY match DESC` 对 NaN 不报错 —— 又是「不报错但全错」。

⚠️ **存储必须用 `sparsevec`。** 1,933 维但每部只有 4.1 个非零值：
`vector` 要 88 MB、`halfvec` 44 MB、**`sparsevec` 实测 0.47 MB**。
为 99.8% 的零付 44 MB 不可接受，而 sparsevec 同样支持 `<=>`，链路形状不变。

⚠️ **P1 的论证框架变了。** 原文档说它对付「区分信息在库里但没进向量」
（大闹天宫→上美影、攻壳→Production I.G），但 **embedding 已经顺手解决了
大闹天宫那个案例**。所以 P1 现在要证明的是「**在 embedding 之上还能再加多少**」，
不是「比 tag 好多少」—— 第 5 周报告要按这个改。
⚠️ 而乐队番那个案例（孤独摇滚 vs MyGO 的基调差异）staff/studio 解决不了，

**5. 问卷选题多样化** —— ✅ **已完成（2026-08-14），但方案与原计划不同**

### ✅ 流程 B 找番（G.1 路径①）—— 单一入口四条分支到此齐了

**做法**：`GET /api/find` 是独立端点（供未来第四个按钮用），`POST /api/ask`
不传 `route` 时，`resolve()` 完全没认出任何作品/角色（`state=unknown`）就是
G.1 设计里那条「④ 以上都不命中 → 流程 B」的触发条件——只是补实现时发现
这条触发条件比设计时想的复杂，见下面两条实测发现。

```
GET  /api/find                 语义找番，零 LLM 生成，只调一次 embedding   src/find.py
POST /api/ask {route:"find"}   按钮强制走找番，跳过 resolve()             server/main.py
POST /api/ask（自动兜底）        resolve() 认不出任何作品 → llm.find_gate()
                                判"是"才展示找番结果，判"否"给套话        server/main.py
```

#### 🚨 BM25 融合已否决 —— 先测再定，同 HyDE 那次的纪律（`scripts/eval_find.py`）

**没有直接凭直觉决定"混不混 BM25"**，用 tag 当 held-out 标签跑了一次
NDCG 对照（复用 eval_hyde.py 的方法论，20 条查询）。⚠️ **多加了一层
eval_hyde.py 不需要的防线**：`search_tsv` 的 B 档就是 tag 名本身
（load_profiles.py 的注释写着「BM25 两档权重 = 标题/别名 + 题材 tag」），
拿 tag 当标签评一条按 tag 建的索引天然循环论证，**按"查询是否字面命中
tag"分组报告**，只有"转述"组（无字面 tag，找番的主要形态——想得起标签名的
用户直接在问卷/标签页筛就行，会来"找番"的恰恰是想不起怎么描述的那批）
才是公平对照：

```
转述查询（n=14）  NDCG@10   semantic 0.576 · bm25 0.221 · rrf 0.448
字面命中（n=6）   NDCG@10   semantic 0.772 · bm25 0.755 · rrf 0.812（噪声量级，n 太小）
```

⇒ **RRF 融合在真正需要找番的场景上是净负收益**——BM25 腿的噪声比信号大，
拖累的是语义腿本来就答对的那部分。与 HyDE 的结论同一个形状（G.5c：多花
一次确定的成本，换统计上为零甚至为负的收益）：**不做**。`find()` 只用
语义腿（`anime_profile.vec`），`scripts/eval_find.py` 留档这个负结果，
不进 `src/`——同 B.4「剥作品名」那次负结果的处理方式。

⚠️ **顺带验证并修了一个 bug**：`plainto_tsquery` 是 AND 语义，多词自然语言
查询几乎全灭（原型实测 5/5 条描述性查询返回 0 行）。`eval_find.py` 里改用
`websearch_to_tsquery` + 停用词过滤，但这只影响评测脚本本身——**没有改
`/search` 端点**，那里的 AND 语义对标题搜索是对的（题目短、要求全词命中）。

#### 🚨 用 LLM 判断"值不值得展示找番结果"，不手写规则/余弦地板（Kevin 2026-08-24 定）

**起因**：语义检索对任何输入都会返回一个 top-k（cos 排序不存在"零结果"），
于是「resolve() 认不出任何作品」不能直接等于「该展示找番结果」——
实测 7 条查询（手测，非正式评测）：在题两条 top1 余弦 0.598 / 0.683，
离题五条里「今天天气怎么样」0.540、「晚饭吃什么好」0.500 都落进了在题
查询的区间——**两类查询的余弦分布有重叠**，样本太小不足以标定可靠阈值。⚠️ 这与 B.4「rerank 分噪声 ~1e-3，绝对地板在物理上调不稳」
同一类坑——**手调一个数字解决不了分布重叠的问题**。

**Kevin 的方案**：调一次 LLM 判断意图，不自己写分类器/阈值；判"无意义"
就返回套话「描述有些模糊不清，能再具体一点吗？」。⇒ `llm.find_gate()`：
一次分类式调用（`max_tokens=5`），system prompt 给了「是」「否」的判例，
只解析第一个字符是不是「是」——**解析要宽容但不能默认为真**，
不确定（含 LLM 调用失败）一律当"否"处理，与「自信地答错很贵，
多问一次很便宜」同一条纪律。

```
判对 7/7（人工挑的边界样本）：
  在题（应判是）  主角很强但很低调的番 · 在异世界开餐厅的故事
  离题（应判否）  今天天气怎么样 · 帮我写一段Python代码 ·
                完全无意义的乱码 · 不存在的声优xyzq · 有什么好看的
```

✅ **随后 Kevin 打了正式的 10 题分（`docs/eval-find-gate-sample.md`）——
9/9 适用题 `gate` 判断与直觉吻合，9/10 `result` 满意。** 唯一的 `n` 是
"今天心情不好，聊聊天吧"——追下去发现 `find_gate` 根本没被调用，`resolve()`
自己把这句话的「今**天心**情」撞上了角色别名「天心」（《罗小黑战记》），
在 `state=unknown` 之前就已经"认出"了一个错误的作品，是一个更早层级的
问题。这个发现直接引出了下面「意图校验」那一整节。

⚠️ **这条改动让 `prompt_digest()` 从两条 system prompt 变成三条**
（`HYDE_SYSTEM` / `ANSWER_SYSTEM` / `FIND_GATE_SYSTEM`）——与「新增影响输出的
配置时要问：它进指纹了吗」同一条纪律，`descriptor()` 的 `max_tokens` 列表
与 `payload` 也同步加了第三项，否则指纹会声称改动前后同源而实际不是。

#### 🚨 全量测试跑出 4 处回归，根因是找番兜底覆盖了更具体的回落文案

第一版实现里，`resolve()` 一旦 `UNKNOWN` 就无条件跑 `find()` 并展示结果，
把 `test_ask_voice_falls_back` / `test_fallback_reason_appears_in_answer`
两条测试原本期望的「没有找到这个名字的声优」覆盖掉了——`route="voice"`
的空结果本来就会把 `route` 改回 `"ask"` 并设 `fell_back`，而找番兜底的判据
只看 `res.state`，没检查 `fell_back` 是否已经带着更具体的失败原因。
⇒ 改成**只在 `fell_back` 为空时才触发找番/gate 那条分支**——与 season 分支
「只在 ask 也没答上来时拼接 `fell_back`」是同一条纪律的第二次应用。

另外两处（`test_ask_unknown_short_circuits` / `test_ask_latin_substring_not_a_mention`）
是找番/gate 的直接目标场景（「明天几点开会」「帮我写一个快速排序的 Python
实现」这类离题问题），第一版无条件展示语义检索结果导致 `state` 从
`"unknown"` 变成 `"ok"`；加上 `find_gate()` 判"否"后这两条恢复原状，
**因为判"否"时 `state` 仍然是 `"unknown"`，只是 `answer` 换了措辞**。
四处修完后 `uv run --group etl python -m pytest tests/ -q`：**215 项全绿**。

⚠️ **顺带的代价**：这四条此前是零延迟、确定性的规则测试（`resolve()`
在非 OK 状态时从不调模型，短路早于那一步），现在会打真实的 `find_gate()`
LLM 接口——全量测试耗时 **93s → 105s**，且理论上引入了模型行为漂移的可能
（`temperature=0` 降低但不消除这个风险）。这是设计本身带来的代价，
不是 bug，记在这里防止将来有人查"为什么这几条测试突然变慢"查半天。

### ✅ 意图校验层（`llm.classify_intent()`）—— 同一天由 find_gate 打分引出

#### 起因：两个洞，一个来自打分表，一个来自我自己追问

`find_gate` 打分表的唯一失分题（见上一节）逼出第一个洞：**`resolve()` 的
字符串匹配在任何 LLM 调用之前就跑完了，会被短别名巧合命中**。追查「今天
心情不好，聊聊天吧」，命中路径是：

```
find_mentions(conn, "今天心情不好，聊聊天吧")
  → 命中 text='天心' entity_type=character character_id=190593
     series_root=159725 title='罗小黑战记'
```

「今**天心**情不好」——「天」是"今天"的最后一个字，「心」是"心情"的第一个字，
两个词碰巧拼出「天心」，撞上《罗小黑战记》真有这么个角色。这不是孤立巧合——
**全库有 16,964 个 2 字符角色别名**（"莉莉"×23、"玛丽"×21 这类高频的还不少），
中文没有空格，不像拉丁别名那次能靠 `norm_name_gaps()` 记录的原文空白位置
判断词边界（`_latin_word_boundary()` 修的是同类问题的拉丁语版本）——**这是
结构性的，不是"天心"一个词的事**。

第二个洞是我自己实测出来的：**除 `voice` 外的按钮分支选错时会"自信地
答非所问"**——`voice` 表现正确纯粹是因为它自己有"找不到人名就回落"的内部
检查，`season`/`find` 没有等价机制：

| 按钮 | 问了不相关的问题 | 实际行为（修前）|
|---|---|---|
| `season` | "灵能百分百讲了什么故事" | 无视问题内容，直接展示"2026年7月番列表" |
| `find` | "三笠的声优是谁" | 语义检索硬凑了一堆"声优"题材番剧，没回答问题 |
| `voice` | "灵能百分百讲了什么故事" | ✅ 正确回落到 ask，答对了剧情 |

#### 设计：一次分类，覆盖 auto + 所有按钮（Kevin 定）

`llm.classify_intent(query) -> tuple[str | None, Provider]`，五选一：
`ask` / `voice` / `season` / `find` / `off_topic`。**每条请求只调一次**，
在 `route`/`reason` 确定之后、进 `with _conn()` 之前调用。

🚨 **首次实测单次调用 11.38 秒**——Qwen/Qwen3-8B 是混合思考模型，默认会先
生成一大段隐藏思维链再吐最终答案，`max_tokens=8` 只截得住可见输出，截不住
思考过程。这个坑 `src/translate.py` 在 2026-08-17 就踩过并记了
`EXTRA_PARAMS["Qwen/Qwen3-8B"]={"enable_thinking": False}`，今天复用同一个
发现——顺手给 `Provider` 加了 `extra: dict` 字段（`_post()` 里
`payload.update(p.extra)`），关掉思考后 **10/10 判对，延迟 0.65–4.3s**。
⚠️ **这道校验每条请求都要跑，不关思考的话延迟会比 `/ask` 本身还夸张**，
整个设计就不成立了——记在这里防止以后换模型/挪配置时把这一步漏掉。

⚠️ **`INTENT_PROVIDER` 独立于 `PRIMARY`/`FALLBACKS` 链，不走 `complete()`**：
这是分类任务不是生成任务，用主力 14B 模型跑划不来，且**每条请求都要跑**，
不像 HyDE/answer 是单次高价值调用。没有配 fallback——分类挂了直接退回
"不校验、信任原路由"，比再换一个模型猜一次更省事也更安全。

**auto 模式下直接采信/改判，按钮模式下只用来"拦不对的"，不用来"静默改判到
另一个具体分支"**：

```
route == "auto"：
  intent == off_topic          → 直接短路，返回"这似乎不是关于动画的问题呢"
  intent 是其他四选一 且 ≠ route → 采用 intent（router.classify() 从不会猜
                                  find，LLM 的判断更细，这正是 [7] 被挡下来的位置）

route 是按钮强制：
  voice   —— 空结果回落**完全不看 intent**（见下面的自我回归）
  season  —— 入口处校验，intent≠season 就在展示列表前拦下来
  find    —— 入口处校验，intent≠find 就在跑语义检索前拦下来
  ask     —— intent==off_topic 时短路（auto 模式已经短路过，这里补的是
             显式 route=ask 的情况，保持前后一致）
```

**为什么按钮模式不能像 auto 一样"静默改判"**：按钮是用户的显式指令，被一次
不保证对的分类结果静默改判到另一个具体分支，风险比"退回通用问答"更高。

#### 🚨 自己写出的一次真实回归：off_topic 短路覆盖了 voice 更准确的话

第一版实现里，`voice` 分支空结果时也去看 `intent`——判 `off_topic` 就短路
返回通用的"这似乎不是关于动画的问题呢"。实测"不存在的声优xyzq"下 `intent`
真被判成了 `off_topic`，于是"没有找到这个名字的声优"这句**已经准确的话**
被一句更含糊的离题提示覆盖掉了。⇒ 改成 **voice 分支的空结果回落完全不看
intent**——它自己的判断已经比通用离题提示更准，不需要"优化"。

📌 这次回归和当年 `_off_topic_response()` 的接口设计有关：**该函数的
`answer` 是写死的**，我最初想通过 `reason` 参数塞进定制文案，但 `reason`
只进 `route_reason` 不进 `answer`，用户实际看到的还是那句通用套话——
**接口设计允许"看起来定制了但其实没生效"，这类 bug 比直接报错更难发现**。

### ✅ 个人中心页（2026-08-24，Kevin 提出）

登录后的个人页：账号信息 + 改用户名/改密码 + 查看和修改已打分的动画。
`AccountPage.tsx` + 三个新端点 + `ratings.list_detailed()`，测试 313 → **329**。

```
GET /api/ratings/detail   评分 + 作品名/年份/热度（个人页列表）    零模型
PUT /api/auth/username    改用户名，**要当前密码**
PUT /api/auth/password    改密码，**要旧密码**
```

#### 🚨 三条实现时的判断

**① 明细单开一个端点，不给 `/ratings` 加 `?detail=1`。** 那个端点的返回
形状被前端**直接转发给 `/recommend`**（schema 注释写着这一点），给它加一个
会改变形状的开关，等于让同一个 URL 有两种契约 —— 调用方少传一个参数就
静默拿到另一种东西。同理 `RatedItem` 与 `Answer` 是两个类型，**别合并**：
合成一个的话前端很容易把整个对象 POST 给 `/recommend`，而那条链路只认
`subject_id/choice/score` 三个字段，多的会被静默忽略。

**② 改用户名也要密码，不只是改密码要。** 会话是 httpOnly cookie，XSS
偷不走 token，**但能直接拿它发请求** —— 不验密码的话一次 XSS 就能改名 +
改密完成账号接管。⚠️ 两个接口的用例都专门断言「密码错时**没有副作用**」：
校验与 UPDATE 写反顺序的话，名字已经改掉了才返回 401，而调用方看到 401
会以为什么都没发生。

**③ 用 PUT 不是 PATCH。** 语义上都说得通，实际理由是 CORS 中间件的
`allow_methods` 里没有 PATCH —— 线上同源不受影响，但**本地开发是
5173 → 8000 跨源**，PATCH 会被预检拦掉：「线上好好的，本地就挂」。
要改成 PATCH 记得同步那一行。

#### 🚨 已知缺口：改密码不会踢掉别处的登录态

JWT 无状态，签发出去的 token 到期（30 天）前始终有效，改密码也一样。
⚠️ **这条对改密码格外要紧**：用户改密码时通常正是怀疑账号被盗，而他会
理所当然地以为「改完对方就被踢下线了」。⇒ 前端那个表单下面**明写了这句话**。
📌 与已记录的「token 吊销做不到 ⇒ 换 AUTH_SECRET 是唯一手段」一致，
不是本次新引入的。⬜ 真要修：给 `app_user` 加 `token_version` 列，签发时
写进 token、校验时比对 —— 代价是 `_current_user()` 从「纯解码、零查库」
变成**每个请求多一次查库**。那是架构取舍，等 Kevin 拍板。

#### 前端：评分的读写仍然只走 session，页面只额外取展示字段

🚨 `AccountPage` 从 `/ratings/detail` 拿的**只有作品名/年份/热度**，
「用户给它打了几分」仍然只从 `useSession()` 的 `answers` 读、只用
`setAnswer` 写 —— 那条铁律没有被这个页面破坏。
⚠️ **行的 choice/score 一律读 answers 而不读快照**，否则用户刚改完分
列表还显示旧值，要刷新才变。
📌 「本页读 `user`」与铁律不矛盾：铁律禁的是「组件自己判断登没登录来决定
评分存哪」，而本页整个存在的前提就是已登录。

⚠️ **移除是软删除 + 可撤销**：点「移除」立刻 `setAnswer(id,'skip')`
（服务端删行，「没看过」用缺失表示），但那一行**仍留在列表里显示为
「已移除」并给一个撤销按钮** —— 撤销回的是快照里的原值，也就是用户
按下移除之前的那一份。直接消失的话点错了就找不回来。

📌 账号卡片**同时显示**「已打分 N 部」（本地视图）与「已同步到账号 N 部」
（服务端 `rating_count`），不一致时给一句提示。挑一个显示的话，同步失败
就是静默的 —— 而防抖批量同步本来就有失败重放这条路径。

#### 🚨 「纯按热度排序」被实测否决了 —— 照字面做会更差

第一版就按字面改成 `fav_done` 降序，跑真实数据一看是倒退：

```
钉宫理惠   「神乐」从第 3 → **第 21**（掉出前 20），前 12 条里 9 条是配角/客串
           《游戏人生》特图、《咒术回战》西宫桃这类路人役顶掉了夏娜、露易丝

           （角色名就叫「花泽香菜」）排第 7，挤掉小渊泽报濑、中野一花
```

**根因**：热门作品的角色**总数**远多于冷门作品 ⇒ 纯热度排序等价于

`DISTINCT ON` 选错代表作，这次是最终排序把它挤出截断窗口。
⇒ 改用 `fav_done × 役别权重`（`ROLE_WEIGHT = {主角 1.0, 配角 0.35, 客串 0.12}`）。
**标定方式**：0.35 让 done=44,372 的配角（《游戏人生》特图）折算成 ≈15.5k，
正好落在夏娜(16.1k) 之后、露易丝(15.6k) 之前 —— **知名配角进得来，
但挤不掉主线代表役**。
⚠️ 这几个权重是**排序偏好不是判据阈值**，与 B.4「rerank 绝对地板调不稳」
不同类：调错了只是顺序略变，不会静默给出错误答案，而且列表本身可直接查验。

⚠️ **`roles_of()` 里有两层排序，别混做一件事**（已写进 docstring）：
① `DISTINCT ON` 内部选代表作 —— role_type 必须压过热度，**别动**；
② 最终列表排序 —— 这次改的是它。

#### 「最近」用规则判，不调模型

`voice.wants_recent()` + `ORDER_RECENT`（年份降序，同年按加权热度）。
⚠️ **只切换排序，不做时间过滤** —— 过滤要标定一个年份阈值（近 1 年？近 3 年？），
而库里最晚 air_date 只到 2026-09-11、候选集 `done>=50` 天然挡住刚开播的新番，
卡紧就返回空列表，用户会以为这位声优近年没作品。排序不丢东西。
📌 时间表达用规则不用模型，与 `router.parse_cour` 同一条纪律。
⚠️ 有意**不收**「新番」「现在」：「她在新番里配了谁」问的是具体作品。

#### LLM 层：`llm.voice_answer()` + `VOICE_SYSTEM`

🚨 **不复用 `ANSWER_SYSTEM`** —— 那条整个是为剧情问答写的（「已知剧情推进到」
「不要丢限定词」），拿它讲配役表，模型会开始声明「资料里没有写到结局」。

🚨 **`max_tokens` 和「会不会抄表」是同一件事的两半。** 首版给 600 且
prompt 只说「不要原样抄」，实测模型仍把整张表抄成 `1./2./3.` 编号清单、
输出 350 字、**单次 34~41 秒**。收紧 prompt（明令不许用编号列表、控制在
150 字）+ 压到 400 + 送进 LLM 的资料从 20 条截到 12 条（`CONTEXT_ROLES`），
三处一起改之后：**132~186 字，3/3 都是连贯段落，没有再抄表**。
（下面这组延迟是**当时还在用 14B** 的数字；后来换成 8B，见下一节。）

```
花泽香菜最近配过什么角色   recent   25.8s  138 字   ← 正确按年份组织：
   「2026 年担纲主角的有《Fate/strange Fake》的绫香·沙条和《当前、正被
    打扰中！》的仲间凛子…该年度她还参与了…但部分角色名未在资料中标注」
花泽香菜配过哪些角色      popular  30.4s  132 字
钉宫理惠的代表作有哪些     popular  36.5s  186 字
```
⚠️ **给的余量越大，模型越倾向于把资料复述完** —— 这条比「在 prompt 里
禁止它」有效得多。

⚠️ **`CONTEXT_ROLES=12` 与返回给前端的 `items` 是两个数，有意不同**：
前端要完整明细（用户会往下翻），模型只需要够它挑 5~8 个来讲。

#### ✅ 为什么最后换成了 8B（`VOICE_PROVIDER`）—— 两轮 A/B，不是凭直觉

用 14B 时延迟是 **26–37 s**（Kevin 已表示可以接受），随后他说「换成 8B 的
看看是不是会快一点」⇒ 跑了对照。**判据不只有延迟** —— G.5f 的教训正是
「按延迟选模型」选出了会张冠李戴的 Hunyuan。这次的四条判据：
延迟 / 有没有抄成编号清单 / 回答里的《作品名》是否全部出现在资料里 /
有没有把「（角色名缺失）」占位符照抄进回答。

```
              延迟(均)      抄清单   资料外作品   漏占位符
第一轮  14B    22.4 s        0/6        1          0/6
        8B      5.4 s        0/6        1        **2/6**   ← 修 prompt 前
第二轮  14B    17.9 s        0/6      **2**        0/6
        8B      7.9 s        0/6      **0**        0/6
最终验证 8B   5.7–6.5 s（voice_answer 真实链路，descriptor 记录 Qwen3-8B）
```

🎯 **8B 不只是快，客观判据上还更干净**：第二轮 14B **两次都**把
《钢之炼金术师 FULLMETAL ALCHEMIST》截短成《钢之炼金术师》，而 8B 老实写
全名。人工读三条也没问题，且 `temperature=0` 下 8B 两轮输出几乎逐字相同，
14B 波动明显更大。
⚠️ **服务端负载波动很大**（14B 两轮均值就差了 4.5 s）⇒ **倍数比绝对值可信**：
两轮里 8B 分别快 4.1× 和 2.3×，方向一致。

🚨 **第一轮 8B 的 2/6 「漏占位符」是我 prompt 写松了，不是模型不行。**
规则 5 原文只说「跳过它，或者如实说明这条记录缺角色名」，8B 选了最字面的
做法 —— 直接把「《XX》的（角色名缺失）」写给用户，看起来像系统故障。
改成明令「绝对不要照抄这几个字，要么跳过、要么合并成一句『另外还有《A》
《B》等几部，资料里没有记录角色名』」之后 **0/6**，而且 8B 的处理比 14B
**更具体**（14B 只说「部分角色名未在资料中标注」，不点出是哪几部）。
📌 教训与 `MAX_TOKENS_VOICE` 那条同形：**小模型对 prompt 的字面依赖更强，
一句话留了模糊余地它就会踩进去** —— 先怀疑 prompt，再怀疑模型。

⚠️ `VOICE_PROVIDER` **独立于 PRIMARY/FALLBACKS，且有意不复用
`INTENT_PROVIDER`**（同一个模型 id，但一个是分类一个是生成，将来任一方
换模型不该牵动另一方）。**没有 fallback**：挂了回落到展示配役表。
⚠️ **必须带 `extra={"enable_thinking": False}`** —— 不关思考的话 8B 会先
生成一大段隐藏思维链，延迟优势直接消失（translate.py 与 classify_intent
都踩过，后者单次 11.38 s）。上面所有数字都是在关掉思考的前提下测的。

📌 `GET /api/voice` **仍然是零模型**，游客可用、即时返回 —— 只有
`POST /api/ask` 的 voice 分支会调 LLM（那条本来就要登录 + 占配额）。

#### 🚨 为什么是用户名而不是邮箱（2026-08-24 Kevin 定）

设计文档 §4 原本写的是 email。改掉的**根因是本项目没有发信能力**
（没有 SMTP / 邮件服务，也不打算加）。由此推出的不是「MVP 先不做验证」
这种权宜，而是三条硬事实：

```
邮箱永远无法验证    验证的唯一手段就是发一封信过去
密码永远无法找回    重置链接同样要靠发信
⇒ 那个 email 字段是一个「无法验证、也无法使用」的字符串，
   实际作用只剩「一个全局唯一的登录标识」—— 而那正是用户名的定义
```

⇒ 收邮箱等于凭空存一份 PII 负债换零收益，与 §4「不存任何 PII」直接相悖。
**用户名严格优于它，不是「差不多」。**

⚠️ **库里存两列**：`username`（原样展示，保留用户写的大小写）+
`username_norm`（判重与登录查询，`auth.normalize_username()` 算）。
📌 与 `alias.norm_name` 完全同一个模式：归一化在 Python 里算，
数据库只对算好的值加唯一约束。
🚨 **特意没用 `UNIQUE (lower(username))` 函数索引**（虽然省一列）：
那样归一化就有两个定义处，而 `casefold()` 与 `lower()` 在边缘 case 上
**并不等价**（德语 ß：casefold 折成 ss，lower 不折）—— 一旦分叉就是
「注册说重名、登录又查不到」这类静默故障。

🚨 **归一化必须做 NFKC，不能只做小写。** 不折全角的话，注册一个
`Ｋｅｖｉｎ` 就能在界面上冒充 `kevin`，而唯一约束**完全看不出问题**。
组合字符（`é` 的两种写法）同理。两条都已加测试锁死。
⚠️ 长度也按归一化后算 —— NFKC 会改变长度，按原始串卡的话有人能用全角
凑出超长名字。

```
POST /api/auth/register|login|logout      注册 / 登录 / 登出
GET  /api/auth/me                         登录态（未登录返回 null，不是 401）
GET|PUT|DELETE /api/ratings               评分持久化
```

🚨 **「登录不是使用门槛」这条原则被修订了一半（Kevin 2026-08-24 定）。**
设计文档反复强调「游客能用全部功能」，现在改成：

> **零模型功能（推荐/问卷/打分/搜索/声优/档期）游客随便用；
> 要花钱调模型的功能（`/ask`、`/find`）需要账号，且每人 24 小时 10 条。**

⚠️ **判据是「这个端点会不会花钱」，不是「它属不属于问答」** ——
`/voice`、`/season` 是纯 SQL，虽然属于问答但对游客开放；
`/find` 只调一次 embedding，但不拦的话它就是**绕过配额的后门**
（同一件事换个 URL 就免费了）。
📌 修订理由是成本结构：问答每条至少两次模型调用（`classify_intent` 校验
+ 生成），而推荐链路全程零模型（A.2）。

#### ✅ 设计文档 §14 那条未决问题可以结案了

原文：「JWT 放 httpOnly cookie 还是 Authorization header —— 前端在 Vercel、
后端在 **Render** 属跨站，cookie 需要 `SameSite=None; Secure` 且要配 CORS

🚨 **那个前提在 2026-08-12 放弃 Render 时就没了** —— 现在前后端同属一个

#### 三个实现时的判断

⚠️ **配额扣费是「先扣后退」不是「先跑后记」。** 后者下并发发 20 条能在计数
之前全部跑完，配额形同虚设 —— 而那恰恰是要防的滥用。代价是请求失败会白扣，
所以 5xx 路径必须 `refund()`。
🚨 **只退服务端故障（5xx）**：「没认出作品」「离题被拦」都是正常业务结果，
照常计费 —— 否则无限问离题问题就能绕过配额。

🚨 **`quota.reserve()` 必须先 `SELECT ... FOR UPDATE` 锁 app_user 那一行。**
不锁的话两个并发请求同时读到 count=9、双双插入 → 11 条，是教科书级的
check-then-act 竞态。锁的粒度是单个用户的行，不同用户零竞争。

⚠️ **库里存 choice 不存算好的分数**（`user_rating.choice` + 可空 `score`）。
这是「前端传 choice 不传分数」那条纪律的**第三次应用**：把
`questionnaire.to_rating()` 的映射结果固化进库，将来调 `WISH_CONFIDENCE`
就得重写全表，而且历史行会带着旧口径静默污染推荐质量。
📌 `ratings.merge_guest()` 用 `DO NOTHING`（**云端为准**，本地只补空缺）、
`upsert_many()` 用 `DO UPDATE`（覆盖）—— **两个函数长得像但语义相反，
不能合并**，各自 docstring 写明了为什么。

#### ⚠️ 已知缺口（都是有意接受的，不是遗漏）

```

token 吊销    做不到（JWT 无状态）⇒ 强制全体下线的唯一手段是换 AUTH_SECRET
```

那一节的三条推论。真要做找回，**前置条件是先有发信能力**，那是另一件事。

🚨 **`AUTH_SECRET` 缺失/短于 32 字符时启动就报错，绝不退回默认值。**
有默认值的话，忘配的部署会**正常启动、正常签发 token**，而那些 token 用的是

✅ **2026-08-24 起找番(find) 也能用了**，四个按钮齐了——见第四部分「流程 B 找番」。

🚨 **三个实现时抓到的问题**：
① 「下一季有什么新番」**静默返回了当季** —— `parse_cour` 不认「下一季」，
   落到默认的「今天所在季度」。用户问下季拿到当季，**从结果里看不出来**。
   ⇒ 补了相对季度表（含跨年：2026 Q3 + 2 → 2027 Q1）。
② **回落原因只写在 `route_reason` 里，用户看不到** —— 实测「下一季」回落后
   `answer` 只有「没认出你问的是哪部作品或哪个角色」，对他毫无信息量，
   真原因藏在一个他不会看的字段里。⇒ 拼进 `answer`，但**只在 ask 也没答上来时**。
③ `ask` 分支原有的 `return` 没带新字段，**回落路径直接 ValidationError** ——
   正常路径全绿，只有走到空结果回落才触发。靠那个用例才暴露。

要修得让 season 支持按 `person_id` 过滤（`voice_role` JOIN + 档期窗口，一条 SQL），
那是新功能不是路由的事。在那之前 **route 回显是唯一的补救**。

### ✅ `GET /api/season` —— 按档期浏览（2026-08-19 上线，上面第 1 步）

窗口口径的唯一定义处是 **`recommend.cour_window(year, month)`**：
本季起点 −7 天 ~ **下季起点（右开）**，宽限沿用 `COUR_GRACE_DAYS`。
上线后实测与本节此前那次测量**逐条吻合**（这就是验收）：
**2016-06-24 ~ 2016-10-01 共 134 部**（默认滤 nsfw；含 nsfw 145）：

```
你的名字。57,748 · 灵能百分百 28,993 · 声之形 27,946 · 齐木楠雄 27,828
ReLIFE 21,494 · 这个美术社大有问题！19,894 · NEW GAME! 15,707
```

- `year/month` 缺省 = 今天（UTC）所在季度 ⇒ 「十年前的这个季度」
  路由层只要传 `year=今年-10`；传 8 月自动归一化到 7 月番。
- ⚠️ 相邻两季窗口在「下季起点前 7 天」**有意重叠**（9/25 开播的既是
  7 月番尾巴也是 10 月番抢跑）—— 别为消除重叠把右端改成 −7 天，
  那会让抢跑新番在「当季」查询里凭空消失一周，理由见 `cour_window` docstring。
- ⚠️ **没挂到 `/recommend` 上**（那个要评分才能算偏好向量，这里是
  无个性化浏览）；`season/aired/upcoming/classic` 四个模式仍只作用于
  `/recommend` 的候选池过滤，两者并行不悖。
- 测试 5 项：窗口两端逐日断言 + 头名《你的名字。》+ 排序/归一化/缺省。

🚨 **自检发现：回溯型查询才有料，当季/未来天生稀薄**（2026-08-19 实测）。

```
2016 年夏季   134 部      ← 「十年前的这个季度」，主力用法，好用
当季 2026Q3    43 部      ← dump 快照最晚 air_date 只到 2026-09-11
下一季          0 部      ← 库内 air_date > 今天的总共只有 2 部
```

**不是本端点的 bug，是候选集 `done>=50` 的口径**（与「`mode=upcoming`
实测只召回 2 部」同一个根因，见「季度更新」①：新番收藏数是 0，
`is_candidate()` 直接返回 False）。⇒ **单一入口的分支③ 拿它答
「下季看什么」会返回空列表** —— 要在路由层给话术，
**不要在端点里放宽窗口**（放宽只会把上一季的旧番混进来冒充新番）。
📌 这条正好给「季度更新」那条待办加了一个具体的触发场景。

⚠️ **顺带纠正一处我自己写错的注释**：端点 docstring 初版写的是
「一条走索引的 SQL」，**实测是 Seq Scan**（5.9 ms / 扫 11,453 行，
`air_date` 上没有索引）。已改。5.9 ms 相对 ~200 ms 跨国 RTT 是噪声
⇒ **不建索引**；照抄 `/api/related` 那句话是错的，那条是
`staff @> jsonb` 命中 GIN。

### ✅ 泛称不参与作用域投票（2026-08-22）

🚨 **触发案例**：「女主角司波深雪的最新进度」→ `ambiguous`，候选是
《魔法科高校的劣等生》/《宝可梦进化》。根因是 dump 里**确实有角色叫「女主角」**
（撞《宝可梦进化》），于是 `司波深雪→魔法科(1票)` vs `女主角→宝可梦进化(1票)`
→ 并列 → 反问，**而用户明明已经点了具体角色名**。
这是 I.1 那条「主角重名 6.4%（アリス×9、主人公×9）」的活体样本。

**修法：`retrieve.GENERIC_NAMES` + 投票时过滤。** 三条设计考虑：

⚠️ **不删 alias 行。** 那是数据 —— dump 里有角色本名就叫「主人公」
（《恶魔幸存者2》），删了那个角色就再也检索不到。只在**投票**这一步忽略。

⚠️ **全是泛称时退回用它们。** 否则「这部动画的主人公是谁」会从
「反问是哪一部」退化成「没认出来」，后者对用户更没用。

🚨 **只能靠语义列举，不能按「撞几部」自动筛** —— 这条最反直觉。实测撞得
最多的**全是真名字**：`爱丽丝 26 部 · マリー 25 · 莉莉 23 · 玛丽 21 · 田中 16`，
而真正的泛称「女主角」**只撞 1 部**。按频率筛会把爱丽丝这类全部误杀、
同时漏掉女主角。⇒ 专门加了一条测试防止有人这么改。

📌 **对 LLM 的理解零影响**（实测确认过）：改的只是 `resolve` 的作用域投票，
**问句原文一字未动**，向量召回和 `llm.answer()` 收到的都是原句。
而且泛称在召回阶段**反而是有用信号** —— 萌娘角色页会写明「本作女主角」：
```
《魔法科高校的劣等生》的女主角是谁   → 0.999 命中「司波深雪…女主角」
《进击的巨人》的女主角经历了什么     → 0.887 命中「《进击的巨人》女主角…」
```
⚠️ 所以两层的作用正好相反又互补：**投票层有害（零指代力却能平票）、
召回层有用（语料里就有这个词）**。当初若按「删 alias 行」的思路修就错了。

### ✅ 词边界与 norm_name 的冲突（2026-08-22 修）—— 拉丁名字整体被否掉

🚨 **两条各自正确的规则复合成了一个静默故障。** `norm_name` 删掉所有空白
（对的，让「Fate/stay night」与「fate stay night」落到同一个键）；
`_latin_word_boundary` 要求拉丁别名落在词边界上（也是对的，实测挡掉过
`Python 实现`→py/hon、`导出成 CSV`→el/ex）。
**但后者依赖的边界，正是前者删掉的东西**：

```
「What happens at the end of Steins;Gate?」
  → whathappensattheendofsteinsgate
  → steinsgate 前面贴着 of 的 'f' → 判为词中截取 → 否决
```

⚠️ **影响面比「英文提问」大** —— 中文问句里同样中招，只要拉丁别名是
**更长拉丁串的一部分**：

| 问句 | 修前 | 修后 |
|---|---|---|
| `CLANNAD AFTER STORY 的结局` | ❌ `[]` | ✅ clannad |
| `Fate stay night Unlimited Blade Works 的结局` | ❌ `[]` | ✅ fatestaynight |
| `Villkiss Michael Mode是谁？` | ❌ `[]` | ✅ villkiss + michael |
| `GIRLS BAND CRY 讲了什么` | ✅ | ✅ **本来就没坏** |

📌 **判据不是「有没有中文名」**（那是 1,380 部 / 12.0%，含 434 部热门：
Fate/Zero · BanG Dream! It's MyGO!!!!! · CLANNAD · OVERLORD）。
**整段拉丁标题被 CJK 包住时一直是好的**，一坏就坏在用户多打一个英文词
——而副标题/篇章名恰恰是这批作品的常态。

**修法**：`textproc.norm_name_gaps()` 记录「原文里紧挨 norm[i] 之前丢掉过
分隔符」，边界判据改成「原文有分隔符 **或** 相邻字符非拉丁」（两支是或）。
⚠️ **不能改成「别去掉空格」** —— alias 26 万行的键就是无空格形态，
改归一化等于全表重灌，还会让变体重新分裂成多个键。
⚠️ `norm_name` **委托**给 `norm_name_gaps`，不留第二份实现（它定义着
alias 的键，漂移就是静默漏召回）——与 `clients.close_all()` 同一条纪律。

**验证（顺带记一个省 CU 的做法）**：`norm_name` 行为经 **313,575 条**对拍
（含 2 万随机 unicode）**不一致 0**；918 题中文对拍 **917 题逐条相同**，
唯一差异是上表 Villkiss 那条（是修复不是回归）。
💡 918 题原本要 ~1,836 次 Neon 往返，**实际只花了 2 条 SQL** ——
既然 `norm_name` 逐字节没变，两版拿到的 DB 行必然相同，差异 100% 在纯
Python 段 ⇒ **把 alias 行批量捞回本地回放**。以后做这类判据 A/B 都该这么干。

### ✅ 结局类问题的「没有」要更有价值（2026-08-23 Kevin 提出，已改）

**要求**：问结局而语料里没有结局时，别只说「资料中没有」，**把已知的最新剧情
给出来**。⚠️ **但不能违反不能胡编乱造的大前提**：所有内容都必须来自给出的
资料；资料里真的什么都没有，就直接回复没有。

**改动**：`llm.ANSWER_SYSTEM` 规则 2 扩写（不是新加规则 —— 它是同一原则的
具体应用，「不要只说资料中没有就结束」那条早就在）。加了两段：
```
例：问结局，而资料只写到剧情中途 → 「资料里没有写到结局。已知剧情推进到：…」，
    把资料里**时间上最靠后**的剧情节点总结出来，明确说这是**已知进度**、不是结局。

```

📌 **先量失败形态再动手，结果把改动范围收窄了**：12 道结局题里**至少 6 道

   规则 3 明明禁止过。**这是本次改动的直接战果，新版整句消失。**
② **[15]《魔法科高校的劣等生》拿元信息充数**：147 字里全是连载日期与卷数。

**实测（12 道结局题，同语料同模型，只换 prompt）**：
```

回答普遍变短：474→277 · 505→373 · 251→157 · 236→157   ← 注水减少
0 处新增的推测性表述
```

🚫 **[15] 没修好，且加严措辞后仍然没修好** —— 它召回的 8 条资料**一句剧情

**prompt 改不了语料里没有的东西。**

### ✅ 解析层清噪声：模板 chrome + 套话前言（2026-08-23）

🚨 **首版把 `toggle-template-button` 也放了进去，删掉 584,805 字 / 126 个页面受损、
4 页被清空** —— 最重的《逆转裁判》86 条 chunk → 21 条。它是 mw-collapsible 的

散文 —— 「注：印象色表示独唱」「日文版由集英社出版」「动画第二话结尾的分数

① 整页只剩这一条时不删（全库 13 页）；

### ✅ 剧情简介席位 —— `summary` 从来不在检索池里（2026-08-23）

**起因**：Kevin 报「《秘密内幕～女子警察的逆袭～》那道题完全没找到关于剧情的语料，
哪怕萌娘页里面有」，并提出「问『讲了什么故事』时强制返回一个剧情简介」。

#### 🚨 诊断：不是"没有语料"，是两层都够不着

```
萌娘的「原作介绍 > 剧情简介」chunk 16689（273 字）就在作用域里，也进了召回池
rerank 排第 6 · 0.0457 —— MIN_SCORE=0.05，差 0.0043 被砍
FINAL=8，它本来排得进前 8。唯一的杀手就是那道地板。
```
⚠️ **与 B.4 那次 songs 一模一样**（层内召回正确、分数被绝对地板砍掉）
⇒ 修法也一样：**加规则，不调阈值**（rerank 分噪声 ~1e-3，绝对地板调不稳）。
📌 rerank 给它低分的原因 B.1 早记过：**查询里的作品名是噪声** —— 元信息章节
（衍生作品/电视剧/番外篇）反复提作品名所以词面匹配高（0.92/0.91/0.81），
而真正的剧情简介只讲故事、一次都不提作品名。

🚨 **但真正的根因在更下面一层：`anime_profile.summary` 从来不在检索池里。**
`plot_chunk` 只装萌娘 prose/songs + dump 角色简介，**作品自己的简介一条没进** ——
而那恰恰是「讲了什么故事」最权威的答案。那部作品的 summary 有 357 字完整剧情，
比萌娘那条 273 字还全。

#### 为什么喂 summary 而不是萌娘的「剧情简介」章节

| 12 道剧情梗概题 | 覆盖 |
|---|---|
| `anime_profile.summary` | **12 / 12**（75 ~ 1307 字） |
| 萌娘剧情类章节 | 9 / 12 |
| 修前前 8 席实际拿到剧情 | **7 / 12** |

⚠️ 而且萌娘那边章节名极度分散（简介 7186 · 剧情简介 1574 · 剧情概要 99 ·
故事简介 97 …），还混着「人物简介」「角色简介」「能力设定」这类**不是剧情**的
⇒ **按章节名批量选就是"按关键词批量删"那个坑**（「游戏中的结局」差点被清掉那次）。
summary 是结构化字段，不需要猜。

#### 实现（`retrieve.SYNOPSIS_QUERY` + `synopsis_context()`）

正则触发 + 三道门：① 问句是剧情梗概类 ② 作用域是**作品**不是角色
（`character_ids` 为空 —— 「张楚岚经历了什么故事」不该塞整篇作品简介）
③ 该 series_root 下有非空 summary。取**热度最高**那部的简介
（与 recommend 的 entry 口径有意不同：那边取最早是为了稳定入口，这边要最有代表性的文本）。

⚠️ **拼成一条普通的 `(section, text)` 走 `related.as_context` 同一个通道** ——
不给 LLM 开第二个信息入口，否则「资料」在 prompt 里有两种含义。
⚠️ **简介 `insert(0)` 排在检索结果之前**：它答的是"整体讲了什么"，chunk 是细节。
⚠️ **出处必须加 Bangumi 条目链接**（`BANGUMI_BASE`，排在萌娘之前）——
LLM 用了它的简介却只标萌娘就是**错误归因**。

#### 实测（12 道剧情梗概题，复用 v5 记录的 chunks 原样重放，唯一变量是有没有简介）

```
3 道原本全灭的题全部答对   [7] 魔弹之王 · [8] 向山进发 · [11] 秘密内幕
2 道明显变好               [4] 一人之下：修前开篇是碧游村支线、赵归真被处决这类
                              中后期细节，修后从「张楚岚 19 岁前隐藏异人身份、
                              被冯宝宝找上」讲起，且原有细节一条没丢
                           [2] 银英：修前只有亚斯提会战 + 鲁道夫建国这些设定，
                              修后讲出完整主线
0 道变差
```
⚠️ **不重跑检索是有意的**：rerank 有 ~1e-3 噪声，重跑会让两侧 chunk 不完全相同，
那就不只测 summary 这一个变量了。
⚠️ 自动拒答判据（正则扫「资料中没有」）**不可用** —— 回答里普遍有
「资料未明确后续剧情」这类**恰当的边界声明**，不是拒答。逐条人工看的。

#### 顺带补上 `NO_CORPUS` 分支（同一个洞的另一半）

`plot_chunk` 覆盖作品 79.3%，而 summary 覆盖 **94.9%**。修前「有 summary 但

实测《爱、死亡 & 机器人》《紫罗兰永恒花园 特别编集版》现在都能答，出处指向 Bangumi。
⚠️ **不违反 G.4 状态③**「检索为空不要丢给 LLM」—— 那条防的是**零资料时模型用
训练记忆流畅编造**，而这里资料真实、有出处，与 related 在本分支的处理完全同构。

#### 🚨 已知缺口：这条路径绕过剧透门控

`anime_profile.summary` **没有 `spoiler_level` 列** —— 它是 Bangumi 条目简介，
长条目本来就会概述全剧。实测《银河英雄传说》(1307 字) 在 `spoiler=False` 下把
「杨威利遇刺、莱因哈特病逝」都讲了。**这是数据源性质，不是 bug。**

🚫 **不靠长度截断来"过滤"结局** —— 结局在后半只是巧合，拿长度当判据与
逆转裁判那个 chrome 阈值是同族的错误。⬜ 若要真修，方向是给 summary 也做
离线剧透标注，那是新工程。

出处链接），总数 188 → **205**。

### ✅ 元信息章节豁免 heimu 剧透门控（2026-08-23，已灌库 406 行）

**起因**：Kevin 报「《神枪少女》在萌娘页上的确有播出时间，却没有召回成功」。

#### 🚨 根因：一句吐槽封杀了整条元信息

```
chunk 7513【衍生作品 > 动画版】176 字，全是播出日期、话数、制作阵容，一句剧情都没有
末句吐槽「原作者表示对1期的风格不怎么感冒」里有 14 字 heimu（8.0%）
⇒ spoiler_level = 1 ⇒ 默认路径下唯一含播出时间的语料被门控挡掉
```
判据在 `parse_moegirl.py`：`1 if (hm > 0 or boxed) else 0` —— **一个字就算**。
⚠️ 而同文件的注释写的是**另一回事**：「算出这段里有多少字来自 heimu，
**再按比例决定**」。注释描述了按比例，实现是有一个字就算。

**规模**：62,651 条 chunk 里 19,790 条（31.6%）标了剧透，**95.1% 靠 heimu**，
heimu 中位占比只有 **7.4%**，83.6% 的剧透标注来自占比 <25% 的 chunk。

#### 🚫 为什么不改成按占比设阈值（那才是注释原本描述的做法）

抽样 60 页的 heimu 实测是**混合用途**：
```
真剧透  「实际是葵的亲生父亲，与世良曾是恋人」「当然，这位是万年卧底」
        「已经成功告白，成为了白银御行的女朋友」「在周刊171话被会长说破其真实身份」
纯吐槽  「凑字的」「看起来压根就是一条哈士奇」「社会我安哥，人狠话不多」
        「岸波白野：石川由依」（声优名）「情报收集终端」
```
而**真剧透往往只占几个字** ⇒ 按占比放行会成片放出真剧透。
⚠️ 与 B.4「rerank 分噪声 1e-3 所以绝对地板调不稳」是同一类错误：
**拿一个与目标无关的量当判据**。

#### ✅ 改用章节语义（`META_SECTION`）

衍生作品／出版信息／相关音乐这类章节按定义就不讲剧情，里面的 heimu 必然是吐槽。
⚠️ **剧透框（`SPOILER_BOX`）不豁免** —— 编者明确声明「以下内容含有剧透」，
出现在元信息章节里也该当真。只豁免 heimu 那一支。灌库前实测「被豁免的 chunk 里
仍带剧透框的 = 0 条」。

```
灌库   series 变更 388 · character 变更 18 · 新增 0 · 孤儿 0 · 冲突 0
       API 请求 0 条（全部缓存命中）⇒ ¥0
       总 chunk 62,651 **一条没变**（只动标注不动切块）
       萌娘 chunk 剧透标注 19,790 → 19,381（31.6% → 30.9%）
效果   《神枪少女》那条从**进不了池子** → rerank 排第 1 · 0.968，播出时间完整答对
```

#### 🚨 顺带修掉一个静默陷阱：`spoiler_level` 没进 digest

`build_plot_chunks` 的增量判据是 `md5(text)` —— **改剧透标注而正文不变时，
灌库会把这些行判为「未变化」静默跳过**：解析层改对了、库里纹丝不动，且不报错。
⇒ digest 改成覆盖 `spoiler_level`（`_digest()` + SQL 侧同步）。
⚠️ **level 放前缀不加分隔符**：Postgres 字符串**不允许含 NUL**
（`chr(0)` 直接报 `ProgramLimitExceeded`），而普通分隔符都可能出现在正文里；
level 恒为一位 ⇒ 第一个字符就是它、其余全是正文，无歧义。
两侧 digest 用**库内真实行**对拍 300 行，不一致 0。
📌 与「新增影响输出的配置时要问：它进指纹了吗」同一条纪律
（`llm.descriptor()` 漏 prompt 那次是同一个坑）。

#### 受影响的评测题：**精确定位到 6 道**，不是 30 多道

粗判据（作用域命中那 406 条覆盖的 series_root）圈出 30+ 道，但那只是"可能变"。
**重跑检索不调 LLM、比较 chunk_id 集合**（判据是集合不是分数 —— rerank 有
~1e-3 噪声，拿分数比会把噪声当变化），实测只有 6 道真的变了：
`4, 5, 11, 12, 52, 54`。只重跑这 6 道的生成侧，其余 54 道一字未动。
📌 [52]《西游记之大圣归来》顺带修好了：现在能拿到「相关音乐」chunk，
正确说明**没有 OP** 并列出 ED 与插入曲（与 [48] 红猪同一类正确行为）。

📌 测试 **10 项**（章节豁免 7 参数化 + 剧情章节回归 + 剧透框不豁免 + 正文不变），
总数 205 → **215**。
⚠️ 写这类测试的坑（已写进 `_spoil()` 的 docstring）：章节名不能随便挑 ——
「制作人员」「各话标题」会被 `KIND_PAT` 判成 credits/episodes，
而 `DROP_KINDS` **整类不入库** ⇒ 一条 chunk 都没有，断言拿到空列表。

### ⬜ 🚨 语料大量是日文原文，跨语言惩罚已实测坐实（2026-08-16）
