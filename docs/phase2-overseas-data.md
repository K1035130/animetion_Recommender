## 0. 与主线的关系（先读这节）

**本文档描述的是另一个产品形态，不是第 1–15 节那个推荐系统的扩展。** 两者工程重心不同：主线是**推荐算法 + 评测严谨性**，本文档是**数据工程 + 实体对齐**。

**已定优先级：推荐系统为主，taste gap 后置。** 第 1–15 节的六周排期照常执行，第 5 周离线评测不动。六周结束后再评估要不要做本文档。

### 已解决的冲突

| 冲突点 | 本文档主张 | 实际采用 | 理由 |
|---|---|---|---|
| 主键 | 「绝不使用外部 id 作主键」 | **保持 `subject_id`（Bangumi id）作主键** | 单源场景下外部 id 作主键更好——幂等、可追溯、少一次 JOIN。内部主键 + 映射表只在真做多源时才划算。真要转多源时再迁移，代价可控 |
| 数据库区域 | AWS `us-west-2`（俄勒冈） | **保持 Neon `us-east-2`（俄亥俄）** | 本文档的理由「加拿大用户 RTT 10–20ms」只对西海岸成立。多伦多/蒙特利尔 → 俄勒冈 ≈ 3,400 km（RTT 60–70ms），→ 俄亥俄 ≈ 600 km（RTT ~15ms）。加拿大 60%+ 人口在东部。且当前主力是国内用户，瓶颈在国际出口不在美国境内距离 |
| 迁移工具 | Alembic | **手写 SQL（`sql/00N_*.sql`）** | 第 1 周只有两张表，Alembic 的收益不抵配置成本。表数量涨到 5+ 或需要回滚时再引入 |

### ⚠️ 未解决：`ingest_raw` 和 `rating_snapshot` 会炸掉存储预算

这是本文档实施前**必须先解决**的硬约束，不是实现细节：

- `ingest_raw`（原始 API 响应留档）：11,453 部 × 3 源 × 5–20 KB ≈ **170–670 MB**
- `rating_snapshot`（时序快照）：每周 × 3 源 × 11,453 部 × 一年 ≈ 179 万行 ≈ **350 MB**

三条出路，实施前必须选一条：
1. `ingest_raw` 的 payload 放 **Cloudflare R2**，Postgres 只存指针（与第 4 节 `plot_chunk` 的 `content_ref` 同一套思路）
2. 快照频率从「每周」降到「每月」，且只对 done≥500 的热门作品做时序
3. 启用第 5 节的**拆库逃生方案**，把摄取层单独放一个 Neon project

## 1. 背景与目标

动漫评分 / 评测站，用户群横跨中国大陆与北美（加拿大）。

**核心差异化功能：跨文化口味差异（taste gap）** —— 同一部作品在国内评分社区与海外评分社区之间的评分落差。这是产品的主要卖点，不是附属功能，架构设计需要围绕它。

典型输出形态：
- 「国内被低估 / 海外被低估」榜单
- 单作品详情页的多来源评分对比
- 按题材、年份、制作公司聚合的系统性偏好差异

## 2. 已做出的架构决策（请勿推翻，除非有明确理由）

| 决策 | 内容 | 理由 |
|---|---|---|
| 数据库分区 | AWS `us-west-2`（俄勒冈） | 加拿大用户 RTT 10–20ms；中国用户瓶颈在国际出口而非距离，选亚太收益有限但会牺牲主力用户 |
| 计算与 DB 同区 | 应用层部署在美西 | DB↔计算延迟会被查询次数放大，必须同区 |
| **不按语言拆库** | 单库 + 多来源维度建模 | taste gap 功能要求跨来源 JOIN，拆库会退化成应用层手动 join |
| 不做 ICP 备案 | 国内访问靠 SSG/ISR + CDN + DNS 优选缓解 | 备案强制要求服务器落地大陆，与当前技术栈互斥 |
| 未来的地理扩展手段 | 只读副本（read replica），不是第二个逻辑库 | — |

## 3. 数据源

所有限流数值以各自官方文档为准，实现时需在代码中验证并做成可配置项。

| 来源 | 类型 | 认证 | 提供的关键数据 |
|---|---|---|---|
| **AniList** | GraphQL `https://graphql.anilist.co` | 无需 key | 英文/罗马音/日文标题、平均分（百分制）、标签、关联作品关系图、`idMal` 字段 |
| **Jikan**（MAL 非官方封装） | REST `https://api.jikan.moe/v4` | 无需 key | MAL 评分（10 分制）、排名、成员数、评分人数 |
| **MAL 官方 API** | REST + OAuth2 | 需注册 client | 数据更权威，但要走 OAuth，可作为 Jikan 的后备 |
| **Bangumi (bgm.tv)** | REST `https://api.bgm.tv` | 需自定义 User-Agent，部分接口需 token | 中文标题、国内评分（10 分制）、**各分段投票人数分布** |
| **TMDB** | REST | 需 API key | 海报/剧照等媒体资源（注意其署名与使用条款） |

**分布数据比平均分重要。** Bangumi 提供完整的 1–10 分段投票人数，这能算出方差、双峰程度等指标；单看平均分会漏掉「两极分化」这类最有意思的差异信号。优先抓取分布。

### 评分口径归一化

三个站的分制和打分习惯都不同（AniList 0–100，MAL/Bangumi 0–10，且 Bangumi 整体分布明显偏移）。

- **原始值必须原样保存**，归一化结果作为派生列或视图
- 线性缩放不可靠 —— 建议用**站内百分位排名**或 z-score 做跨站可比化
- 归一化逻辑要能独立重算，不要写死在导入脚本里

## 4. 实体对齐（本项目最大的技术风险）

跨站匹配同一部作品是这类项目翻车率最高的环节。

**对齐锚点，按可靠度排序：**
1. `mal_id` —— AniList 有 `idMal` 字段，Bangumi 部分条目也带 MAL 关联，这是最强锚点
2. 罗马音标题 + 首播年份 + 作品类型（TV/剧场版/OVA）精确匹配
3. 标题模糊匹配（归一化后计算编辑距离）—— **仅作候选，不自动落库**

**已知的坑：**
- **分季差异**：Bangumi 常把每一季当独立条目，MAL 也是，但 AniList 的处理方式在部分作品上不一致
- **剧场版归属**：总集篇剧场版 vs 完全新作剧场版，各站分类不同
- **译名多样**：中文译名存在台版/港版/民间翻译多套并存
- **同名不同作**：翻拍、重制版

**要求：低置信度匹配落到人工复核队列表，不直接写主表。** 宁可漏，不可错 —— 错误的实体合并会污染整个 taste gap 计算，且事后极难发现。

## 5. 数据模型草案

```sql
-- 作品实体（内部主键，绝不使用外部 id 作主键）
anime(
  id, canonical_title, romaji_title, media_type,
  season_year, season, episode_count, aired_from, aired_to
)

-- 外部 id 映射
anime_external_id(
  anime_id, source, external_id,
  match_confidence, match_method, verified_at
)
-- source ∈ {'mal','anilist','bangumi','tmdb'}
-- UNIQUE(source, external_id)

-- 多语言文案
anime_i18n(anime_id, locale, title, synopsis)

-- 评分快照（时序，保留历史以便看趋势）
rating_snapshot(
  anime_id, source, captured_at,
  score_raw, score_scale, vote_count,
  score_distribution JSONB,   -- {"1": 12, "2": 30, ...}
  rank, popularity
)

-- 原始响应留档，便于重跑与排查
ingest_raw(source, external_id, fetched_at, payload JSONB)

-- 人工复核队列
match_review_queue(
  candidate_anime_id, source, external_id,
  confidence, signals JSONB, status
)
```

派生的 taste gap 用**物化视图**，定时刷新，不要在请求路径上实时算跨表聚合。

## 6. 同步策略

- **全量 backfill**：一次性 CLI 脚本，支持断点续传（记录游标），支持按来源单独跑
- **增量更新**：定时任务。热门作品高频、冷门作品低频，做分级调度
- **执行环境**：优先 GitHub Actions 而非 Vercel Cron —— 长时间抓取任务不受函数超时限制，也便于本地复现
- **幂等性**：所有写入走 upsert，同一批数据重跑不产生副作用
- **限流与退避**：尊重各源限流，指数退避 + jitter；限流参数集中配置
- **原始快照**：先落 `ingest_raw`，解析与写主表作为独立阶段 —— 解析逻辑变更时不必重新请求外部 API

## 7. 明确不要做的事

- ❌ 按语言拆成两个数据库
- ❌ 用外部平台的 id 作为内部主键
- ❌ 爬网页 —— 上述来源都有 API，抓 HTML 既脆弱又踩服务条款
- ❌ 抓取并存储用户评测正文 —— 评测文本有版权，只存**评分数值、统计分布、原文链接**
- ❌ 模糊匹配结果自动合并实体
- ❌ 在页面请求路径上实时计算跨来源聚合

## 8. 建议的第一批任务

1. Alembic migration：建上述表结构
2. 三个 API client（AniList / Jikan / Bangumi），各自封装限流、重试、UA 声明，统一接口
3. `ingest_raw` 落库层 + 解析层分离
4. 实体对齐脚本：置信度打分 + 复核队列
5. backfill CLI（`--source`、`--since`、`--resume`）
6. taste gap 物化视图 + 刷新任务

先跑通一个小样本（比如 2024 年的 TV 动画，约几百条）验证对齐准确率，再做全量。
